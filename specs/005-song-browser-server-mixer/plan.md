# Implementation Plan: Song Browser, Song Server and Channel Mixer

**Branch**: `main` | **Date**: 2026-10-20 | **Spec**: [spec.md](spec.md)

## Summary

Five parts, built in this order.

**1. Channel mixer** (story 1):
- `chip-synth.js` and `sound-packs.js` render one stem per channel (P1, P2, TR, NO).
- `player.js` plays the four stems through four gains, an arrangement bus and a limiter, so a
  level change is a gain ramp and playback never restarts.
- The default levels are measured on the 8 examples ([research R1](research.md)).
- A new `audio/wav.js` writes the WAV download from the stems with the current levels.

**2. Track preview** (story 2): a pure `previewWindow` in `plain-synth.js` picks the bars to
play, and `main.js` `previewTrack` renders only those bars.

**3. Catalog data** (stories 4 and 6):
- `src/catalog/analysis.py` (new) computes analysis facts per MPB MIDI file. It reads the local
  study copy and reuses `read_lead_sheet_midi` plus a port of the app's melody-track ranking.
- `src/catalog/authors.py` resolves death years on Wikidata.
- `src/catalog/collections.py` writes the ABC lead sheets of the public-domain MPB songs,
  Nottingham and the PDMX subset.
- The catalog is split per source into `arranger/data/catalog/<source>.json`.

**4. Song server** (stories 4 and 5):
- A Starlette app in `server/` (`server/app.py`, `server/sources/*.py`) reuses `src/leadsheet`
  for reductions and `src/catalog` for the analysis.
- All network access goes through one injected `Fetcher`: allow-list, caps, sniffing, per-host
  spacing and an LRU cache.
- Tests use a fake fetcher and never touch the network.

**5. Song browser** (story 3):
- A memory-card browser in the style of the PS2 BIOS:
  - `arranger/src/ui/song-browser.js` holds the DOM, the state and the keyboard handling;
  - `arranger/src/ui/browser-scene.js` holds the three.js scene;
  - sprites come from `arranger/src/ui/sprites.js`;
  - sources come from `arranger/src/core/sources.js` (catalog loading, search across cards,
    loading routes).
- It replaces the Song card's tabs and hands songs to the unchanged `createInputPanel`
  (`readFile`).

**Deployment:**
- A `Dockerfile` and `.github/workflows/server-image.yml` publish
  `ghcr.io/giowgiow/nes-arranger-server`.
- `deploy/homelab/nes-arranger/` holds the kustomize manifests, copied into the homelab
  repository after the student approves.

## Technical Context

- **Languages:** JS ES2022 modules (app, no build) and Python 3.12 (CLI and server).
- **New dependencies:**
  - three.js 0.186.1, vendored (`arranger/vendor/three/three.module.min.js`, MIT).
  - `starlette`, `uvicorn` and `httpx` in a new uv dependency group `server`, pinned in
    `uv.lock`. The CLI does not need them, and the tests need nothing new: Starlette's
    `TestClient` uses httpx.
- **Testing:**
  - `node --test` (app).
  - pytest (`tests/`, including the new `tests/server/` and `tests/catalog/`), with a fake
    fetcher and no network.
- **Data inputs, never committed:**
  - `~/ufmg/music_gen/datasets/beakauffmann/` (3,760 MIDI files plus `metadata.csv`), passed with
    `--dataset`.
  - `data/raw/pdmx/` (`PDMX.csv` and `mid.tar.gz` from Zenodo 15571083).
  - `data/raw/nottingham/` (git clone of `jukedeck/nottingham-dataset`).
  - `data/raw/wikidata/` (SPARQL cache).
- **Performance goals:**
  - Mixer level change in ≤0.1 s.
  - Browser ≥30 fps while moving through a card of 3,000 songs.
  - The first paint loads no catalog other than Examples.
  - Server: an MPB song in ≤5 s.
- **Constraints:**
  - The NES render with default chip gains is unchanged, so the Korobeiniki SHA pin and chip
    parity hold.
  - Samples and parity fixtures are unchanged (SC-008).
  - The agent never reads The Session's tune data ([research R9](research.md)).

## Constitution Check

| Principle | Check | Status |
|---|---|---|
| I. Reproducibility | Sprites are seeded from the catalog's sprite seed through `core/random.js`. Catalog files are regenerated byte for byte by documented commands from recorded inputs. The GA is untouched. | Pass |
| II. Test-first | Every module starts with a failing test: stems, mixing, WAV, preview window, sprites, card windowing, loading routes, catalog analysis, authors rule, collection writers, fetcher rules, server endpoints. | Pass |
| III. Representation | Analysis facts and lead sheets use the existing lead-sheet model. Seconds appear only in audio. | Pass |
| IV. Learnable code | Every new module has a header that explains its idea: stems and gain staging, PS2 browser layout, public-domain rule, fetcher safety. Public functions have docstrings or JSDoc with examples. | Pass |
| V. Visual | The browser shows the catalog visually, and the details panel shows the analysis facts. | Pass |
| VI. Evaluation | Mixer defaults are measured (R1), and catalog coverage is counted (SC-004, SC-005). | Pass |
| VII. Simplicity | One vendored library and one small service. Each source module is about 100 lines. | Pass |
| Third-party material | MPB: analysis facts only, notes on demand, temporary cache. ABC only for public-domain songs or licensed collections, with license files. The Session only from the browser to its API. | Pass |
| Web App Constraints | Core logic stays pure (sprites, windowing, search, preview window, mixing math). Web Audio stays in `player.js`, WebGL in `browser-scene.js`. The app works without the server. | Pass |
| Song Server Constraints | Allow-list, caps, sniffing, per-host spacing, per-IP limits, CORS, denylist, no visitor logs, mocked tests. Private ranges are blocked twice: by a NetworkPolicy and by an address check in the fetcher. | Pass |

**Structure decision:**
- The server sits in `server/` next to `src/`, because it imports `src/leadsheet` and
  `src/catalog` directly. Run it with `uv run --group server server/app.py`.
- The homelab manifests live here as a deployable copy. They are copied into the homelab
  repository, which ArgoCD reads, only after the student approves.

## Complexity Tracking

| Item | Why needed | Simpler alternative rejected because |
|---|---|---|
| three.js (vendored, ~700 KB) | The 3D memory-card browser the student asked for | Hand-written WebGL would be more code to teach than the scene itself |
| A server process | Browsers cannot read other sites' files (CORS), and MPB songs must not be committed | Download-and-drop is the old flow the student rejected |
